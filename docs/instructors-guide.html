1. The Course in a Nutshell

Collecting Digital Data is a one-day (10:00–16:00) online training course for social science PhD students, delivered as part of the Scottish Graduate School of Social Science (SGSSS) methods training programme. It introduces two core techniques for collecting data from the web — web scraping and APIs — and a modern skill — using LLMs as coding assistants.

Course philosophy
The course prioritises APIs over web scraping. Web scraping is taught first (one practical) to establish the request–parse–extract–save pattern, but the majority of the day is spent on APIs (two practicals + a challenge). This reflects the reality that APIs are more reliable, more ethical, and more commonly used in contemporary computational social science.

Target audience

  • Social science PhD students with no prior programming experience required
  • Students choose either Python or R — all practicals are available in both languages
  • All code runs in Google Colab (no local installation needed)

Learning outcomes

By the end of the course, students will be able to:

  1. Explain how the web works (HTTP requests, HTML, JSON) and why this matters for data collection
  2. Write code to scrape data from a website using a request–parse–extract–save workflow
  3. Use a web API to collect structured data, handling parameters, pagination, and rate limits
  4. Navigate API documentation and apply the same data collection pattern to unfamiliar APIs
  5. Critically evaluate LLM-generated code and understand when to trust (and not trust) it

Before the course

  1. Share the course README with students at least 2 days in advance. It contains links to all notebooks and setup instructions.
  2. Check that Colab links work. Test each "Open in Colab" badge for both Python and R notebooks.
  3. Compile the slide decks. Run pdflatex (with --shell-escape for minted) on each lecture .tex file. The preamble file must be in the same directory.
  4. Test the APIs. The UK Police API, Parliament API, World Bank API, and ONS API are all free and require no authentication, but availability can vary. Run each notebook end-to-end the day before.
  5. Prepare a backup plan. If an API is down, the notebooks can still be discussed using the expected output. Consider having screenshots of key outputs.

During the course

Delivery model: Short lectures + self-paced practicals
The course alternates between short lectures (15–30 min) and longer self-paced practicals (35–60 min). This was the most praised aspect of the course in student feedback (6/8 students). Resist the temptation to extend lectures — keep them tight and let students spend time coding.
  • Lectures: Present the Beamer slides. Keep to time. Use the "Research in Action" slides to connect techniques to real social science research.
  • Practicals: Students work through notebooks at their own pace. Monitor the chat (if online) or circulate (if in person) for questions. Do not present the notebooks — students read and run them independently.
  • Exercises: Each practical ends with an exercise. Students who finish early can attempt stretch tasks or explore alternative data sources. Students who don't finish the exercise can refer to the solution in the appendix.
  • Pacing: Students work at different speeds. The exercises and stretch tasks provide natural differentiation. Do not hold back fast students or rush slow ones — the notebooks are designed for asynchronous reference after the course.
  • Technical issues: Most issues relate to Colab runtime (R kernel not selected, runtime disconnected). A quick troubleshooting check: "Have you selected the right runtime?" covers 80% of problems.

After the course

  • Share the course materials (notebooks, slides, reading list) for students to keep
  • Collect feedback using the SGSSS feedback form
  • Review feedback and update materials for the next iteration

4. Pedagogy

Overarching approach

The course follows a short-lecture-then-practice model inspired by Software Carpentry and Data Carpentry workshops. Each topic is introduced with a brief, focused lecture (15–30 minutes) that establishes conceptual foundations, immediately followed by a longer self-paced practical (35–60 minutes) where students apply what they've learned by writing and running code.

Why this works
Research on teaching programming to novices (e.g., Barba et al., 2019; Wilson, 2014) consistently finds that:
  • Active learning outperforms passive instruction — students learn to code by coding, not by watching
  • Short feedback loops (write code → run it → see output) build confidence and catch misunderstandings early
  • Worked examples followed by similar exercises are more effective than abstract instruction for beginners

Notebook design principles

The Jupyter notebooks are the primary learning resource. They are designed with the following principles:

1. Scaffolded progression

Each notebook follows a consistent arc: simple example → realistic example → independent exercise. The simple example (e.g., scraping a single page) establishes the core pattern with minimal complexity. The realistic example (e.g., scraping an A-to-Z directory) adds loops, error handling, and data management. The exercise asks students to apply the same pattern to a new dataset with skeleton code and gaps to fill.

2. Rich markdown scaffolding

Every code cell is preceded by a markdown cell that explains what the code does and why. This serves two purposes: during the course, it helps students understand unfamiliar code before running it; after the course, it makes the notebooks useful as reference material. Key code blocks include "What this code does" annotations that describe the logic in plain English before students encounter the syntax.

3. Self-contained and language-parallel

Each notebook is fully self-contained — it includes all imports, data, and instructions needed to run from start to finish. Every practical is available in both Python and R, with equivalent functionality and identical explanatory text. This allows students to choose their preferred language without missing any content.

4. Exercise design

Exercises use a skeleton-code-with-gaps pattern: the overall structure is provided, but key lines are replaced with # INSERT CODE HERE comments. This reduces the blank-page problem while still requiring students to think through the logic. Full solutions are provided in an appendix at the end of each notebook. Exercises also include a flexibility note encouraging students to bring their own data or use a different API if preferred.

5. Pseudo-code before real code

Before introducing any multi-step workflow, the notebooks present it as pseudo-code — a plain-English description of the algorithm. This cultivates computational thinking (breaking problems into steps) before students engage with language-specific syntax.

Lecture design principles

  • Short and focused: 15–30 minutes maximum. Lectures establish conceptual foundations; practicals build skills.
  • Visual explanations: TikZ diagrams illustrate abstract concepts (HTTP cycle, API architecture, JSON structure, LLM workflow).
  • Research in Action: Each lecture includes a slide showing published social science research that uses the technique being taught, grounding the method in real scholarly practice.
  • Accessible design: WCAG AA contrast ratios, minimum 20pt body text, no colour-only information, Fira Sans/Mono fonts for readability.

Differentiation

Students arrive with varying levels of programming experience. The course handles this through:

  • Self-pacing: Faster students can work ahead; slower students can take more time on earlier sections
  • Stretch tasks: Practical 3 includes optional Task 4 extensions for advanced students
  • Flexible exercises: Students can use the provided dataset or bring their own
  • Solution appendices: Students who get stuck can check the solution and continue learning
  • Asynchronous reference: Notebooks are designed to be useful after the course for self-study

Future improvements to consider

More time on practicals (3/8 students)
The most common suggestion. The current schedule is already tight. Options: (a) reduce Lecture 1 from 30 to 20 min by moving the ethics slide into Practical 1's introductory text; (b) make Practical 4 (LLM Showdown) optional/homework, freeing 35 min for earlier practicals; (c) extend the course to a full 6 hours (10:00–16:30).
Peer learning / breakout rooms (1/8 students)
Consider adding a brief breakout activity during Practical 3 (API Challenge) — for example, pair students who chose different APIs and have them explain their approach to each other. This would add variety and peer learning without requiring additional content.

Other ideas for future iterations

  • Activity variety: One student noted that 5 hours is tiring even with breaks. Consider adding a short non-coding activity (e.g., a "find the API" scavenger hunt during Lecture 3, or a live polling question during Lecture 4).
  • Pre-course preparation: Offer an optional 30-minute "Python/R basics" video for students with zero programming experience, so they arrive comfortable with variables, loops, and function calls.
  • Post-course office hours: Offer a 30-minute drop-in session 1–2 weeks after the course for students who are applying the techniques to their own research.
  • Authentication: The current course avoids APIs that require authentication. A future version could include a brief section on API keys (e.g., using the OpenAI API with a key), as many research-relevant APIs require this.
  • Error handling depth: The notebooks use basic try/except (Python) or tryCatch() (R). More advanced error handling (retries, exponential backoff) could be added as an appendix for interested students.
  • Data ethics case study: Replace or supplement the ethics bullet points in Lecture 1 with a short case study (e.g., the Clearview AI scraping controversy, or the Cambridge Analytica API misuse) to make the ethical discussion more concrete.

Technical maintenance

  • API availability: Test all API endpoints before each delivery. The Edinburgh Council directory pages may change structure. The ONS API is in beta and may change.
  • Google Colab updates: Colab occasionally changes its interface or default package versions. Test notebooks in Colab before each delivery.
  • LaTeX compilation: The Beamer slides require pdflatex --shell-escape (for minted syntax highlighting), plus the packages listed in sgsss-beamer-preamble.tex. A full TeX Live installation is recommended.
